多言語サイトのAI検索対策：言語ごとに正しく読ませるための、制作会社の設計と確認の手順

多言語サイトをAIや検索に正しく読ませるには、「1つのページに1つの言語」「言語ごとに別のURL」「hreflang で各言語のページを相互に結ぶ」「営業時間・価格・住所などの事実をすべての言語で同じにする」の4つを、作るときと毎月の保守で確かめるのが基本です。Googleは、ページの言語を lang 属性や hreflang ではなく、見えている本文から判断すると説明しています。ChatGPTやPerplexityが hreflang をどう扱うかは公式の説明がなく、試した例では英語版を出典にすることも多いため、どの言語のページを出典にされても事実が正しいことが大事です。

作成日：2026年11月24日（JST）。対象は、インバウンド向けの宿泊・飲食・観光、海外の取引先がある製造業、外国人の患者さんを受け入れる医院などの多言語サイトを作る・保守する制作会社とフリーランスの方です。Googleの説明は、この記事の作成時点の Search Central の文書に合わせています。

AIの回答は日や聞き方、使う人の言語の設定によって変わります。この記事の手順は、AIや検索に正しく読まれるための前提を整えるもので、AIの回答に出ることや順位を保証するものではありません。

よく読まれている記事と、足りないこと

「多言語サイト AI検索」「インバウンド 多言語 LLMO」「multilingual GEO」などで上位に出る日本語6本・英語6本を、2026年11月24日に読みました（日本語1本は別のサイトに転送されたため読んでいません）。日本語では、uravation（2026年9月5日更新）、DeepLのブログに載ったWeglotの記事（6月19日更新）、GOOD LUCK TRIP（2025年3月21日更新）、JNTO（日本政府観光局）のインタビュー（9月30日）、Digima（3月11日）。英語では、GSQi（Glenn Gabe、2025年12月1日）、Weglot（8月10日更新）、RWS（4月28日）、Lokalise（11月16日）、eSEOspace（10月13日）、MultiLipi（5月27日）です。

英語の上位記事の多くは翻訳ツールの会社のもので、「翻訳するとAIでの引用が数百％増える」といった数字が、調べ方の説明なしに載っていました。日本語の記事はAI検索に触れていないものも多く、次の点はほとんど書かれていませんでした。

翻訳ツールの会社による引用の増加率などの数字は、件数や調べ方が書かれていないため使っていません。
足りない点この記事で書いていること
「hreflang を入れる」とだけあり、書き方の例と、相互に結ばれているかの確かめ方がないコードの例と、相互の結びつきを確かめるスクリプト
Googleの説明と、AIについて分かっていないことが分けて書かれていない公式の説明・観察の例・分かっていないことの表
言語ごとにずれやすい事実（営業時間・価格・電話番号など）の扱いがない言語でそろえる事実と、言語ごとに変えるものの表
WordPress（Polylang・WPML）での手順がないプラグインごとの hreflang の出方と、公開前に見る場所
制作会社の見積もり・保守での扱いがない見積もりに書く範囲の表と、毎月の確認の項目

わかっていること・わかっていないこと

多言語サイトのAI対策では、検索エンジンの公式の説明と、AIについての推測が混ざって語られがちです。お客様への説明では、次のように分けておくと誤解がありません。

内容分類と出典
Googleはページの言語を、見えている本文から判断する。lang 属性やURLは使わないGoogleの説明（多言語・多地域のサイトの管理）
Googleは hreflang や lang 属性を言語の判定には使わない。hreflang は、同じ内容の各言語版をGoogleに知らせるためのものGoogleの説明（ローカライズ版について知らせる）
2つのページが互いを指していないと、その hreflang は無視されるGoogleの説明（ローカライズ版について知らせる）
AIで訳した内容は、それだけでスパムとはされない。ただし、価値の少ないページを大量に作ることはスパムのポリシーの対象で、その例に「翻訳などの自動の変換」が入っているGoogleの説明（スパムに関するポリシー、GoogleのコメントはSearch Engine Roundtable・GSQi、2025年6月）
Bingでは、hreflang は content-language よりずっと弱い手がかりBingの担当者の発言（Search Engine Roundtable、2020年9月。古い発言なので今も同じかは不明）
ChatGPT・Perplexity・Claude が hreflang を読むか、どの言語のページを出典に選ぶか公式の説明は見つからず、分かっていない

参考になる観察の例として、SEOコンサルタントの Glenn Gabe が、Googleの文書やCloudflareの記事など、各言語版があるページについてフランス語・イタリア語・スペイン語で各AIに質問し、出典のURLの言語を記録しています（GSQi、2025年12月）。GoogleのAIモードとAIによる概要、Copilotは質問の言語に合ったページを出すことが多く、ChatGPTとClaudeは3つの例すべてで米国の英語版を出典にしていました。Perplexityは1つの例だけ正しい言語でした。例は3つだけで、本人も「完璧な方法ではない」と書いているので、傾向の参考にとどめてください。

このため、制作会社としては「AIに各言語のページを選ばせる」ことより、「どの言語のページが出典にされても、事実が正しく、ほかの言語のページへたどれる」状態を作ることを目標にするのが現実的です。

設計で決めること：URLの分け方と、言語の切り替え

Googleは、言語ごとに別のURLを使うことをすすめ、Cookieやブラウザの設定でページの言語を切り替えることはすすめていません。URLの分け方には次の選択肢があります。

Googleの「多言語・多地域のサイトの管理」の表をもとに、制作会社の判断の目安を足しています。
分け方向いている場合と注意
サブディレクトリ（example.jp/en/）1つのドメインで管理でき、WordPressの多言語プラグインでも作りやすい。中小のサイトではまずこれを検討する
サブドメイン（en.example.jp）言語ごとに別のサーバーやシステムを使う場合。URLだけでは対象の国が分かりにくい
国別のドメイン（example.de など）国ごとに会社や在庫が違う場合。費用と管理の手間が大きく、ドメインごとの条件もある
URLのパラメータ（?lang=en）Googleは非推奨としている。新しく作るサイトでは使わない

言語の自動の切り替え（IPアドレスやブラウザの言語を見て別の言語のページへ転送すること）は避け、各ページに他の言語へのリンクを置きます。Googleは、Googlebotは通常米国から、Accept-Language を送らずにクロールすると説明しており、自動の転送があると一部の言語のページが読まれないおそれがあります。AIのクローラーも同じように、決まった場所から言語の指定なしで来ることが多いと考えておくと安全です。

1つのページには1つの言語だけを書き、原文と訳を並べる形は避けます。ナビゲーションやフッターだけを訳して本文が日本語のままのページは、Googleでは重複として扱われやすくなります。訳していない本文のページは、その言語のページとして作らない方が安全です。

どの言語でもそろえる事実と、言語ごとに変えるもの

AIが英語版を出典にして日本語で答えることもありえます。言語ごとに更新の時期がずれると、古い営業時間や価格が別の言語で答えられます。次の表のうち「そろえる」ものは、すべての言語で同じ値にします。

項目そろえる／変える
営業時間・定休日・臨時休業そろえる。日本語だけ更新して他の言語が古いままになりやすいので、更新の手順に全言語を入れる
価格・税込か税抜か・通貨金額はそろえる。日本円の価格は他の言語でも円で書き、参考の外貨は「目安」と書く
電話番号そろえる。海外からかける人のために +81 の形も書く
住所・地図同じ場所を指す。英語では番地・町名・市区町村・都道府県・郵便番号の順など、その言語で通じる書き方にする
店名・会社名正式な表記を1つ決め、他の言語ではローマ字や訳の名前を添える（例：Sakura Soba（さくら蕎麦））
予約・問い合わせの方法そろえる。外国語で受けられない窓口は、その旨を書く
対応できる言語・支払い方法・アレルギー表示などその言語の利用者が知りたいことを足す。事実は日本語のページにも書く
見出し・説明の言い回し変える。直訳ではなく、その言語で検索される言い方にする

JNTOのインタビュー記事でも、訪日旅行者が生成AIで情報を集めるようになり、多言語サイトでは事実を分かりやすく書くことが大事だと述べられています（JNTO、2026年9月30日）。

hreflang の書き方と、よくある間違い

hreflang は、HTMLの link 要素、HTTPヘッダー、サイトマップのどれで書いてもよく、Googleはこの3つを同じものとして扱います。WordPressでは、多言語プラグインが head に link 要素を出すのが一般的です。書き方の例は次のとおりです。

<!-- 例：アクセスのページ（日本語・英語・繁体字・韓国語）。
     4つの言語のページすべてに、同じ5行を入れる（自分自身の行も入れる） -->
<link rel="alternate" hreflang="ja" href="https://example.jp/ja/access/">
<link rel="alternate" hreflang="en" href="https://example.jp/en/access/">
<link rel="alternate" hreflang="zh-Hant" href="https://example.jp/zh-hant/access/">
<link rel="alternate" hreflang="ko" href="https://example.jp/ko/access/">
<link rel="alternate" hreflang="x-default" href="https://example.jp/en/access/">
よくある間違い正しい形
日本語のページだけに入れ、英語のページには入れていないすべての言語のページに、自分自身を含めた全言語の行を入れる（相互に指していないと無視される）
相対パス（/en/access/）で書いているhttps から始まる完全なURLで書く
jp・en-UK・es-419 などの誤ったコード言語は ISO 639-1（ja・en）、地域は ISO 3166-1（en-GB）。国のコードだけは使えない。中国語の繁体字は zh-Hant または zh-TW
転送されるURLや、noindex のページを載せているそのまま表示される、検索に出してよいページだけを載せる
翻訳していないページにも全言語の行を出している訳したページだけを載せる。訳が後から増えるなら、増えたときに行を足す

x-default は、どの言語にも当てはまらない人に見せるページです。言語を選ぶページや、海外の人の多くが読める英語版を指定するのが一般的です。

このサイト（nurevo.jp）も41の言語で記事を出していますが、日本語と英語しかない記事では、hreflang に日本語・英語（と英語の地域）・x-default だけを載せ、訳を足したときにその言語の行を足しています。存在しない言語のページを載せないためです。

相互に結ばれているかを確かめるスクリプト

プラグインが hreflang を出していても、一部のページだけ訳がない、URLを変えた、転送を入れたといった理由で、相互の結びつきが切れることがあります。次のスクリプトは、1つのページから各言語のページを開き、互いに載せているかと、html の lang 属性を一覧にします（Python 3 の標準ライブラリだけで動きます）。

# 使い方：python3 check_hreflang.py https://example.jp/ja/access/
# 指定したページの hreflang に載っている各言語のページを開き、
# そのページも「自分自身」と「指定したページ」を載せているかを確かめる。
# 結果：OK／NOT_RECIPROCAL＝相互に載っていない（Googleはこの組を無視する）
#       REDIRECTED＝載っているURLが転送される／NOT_ABSOLUTE＝完全なURLでない
#       html_lang の列で、<html lang> がその言語になっているかも見る
import re, sys, urllib.request

def fetch(url):
    req = urllib.request.Request(url, headers={"User-Agent": "Mozilla/5.0 (hreflang-check)"})
    with urllib.request.urlopen(req, timeout=20) as res:
        return res.geturl(), res.status, res.read().decode("utf-8", "replace")

def alternates(html):
    found = {}
    for tag in re.findall(r"<link\b[^>]*>", html, re.I):
        if not re.search(r'rel=["\']?alternate', tag, re.I):
            continue
        lang = re.search(r'hreflang=["\']([^"\']+)', tag, re.I)
        href = re.search(r'href=["\']([^"\']+)', tag, re.I)
        if lang and href:
            found[lang.group(1).lower()] = href.group(1)
    return found

def html_lang(html):
    m = re.search(r"<html\b[^>]*\blang=[\"']([^\"']+)", html, re.I)
    return m.group(1) if m else ""

start = sys.argv[1]
final, status, html = fetch(start)
base = alternates(html)
if not base:
    sys.exit(f"{start}: no hreflang links found")
print("hreflang\turl\tstatus\thtml_lang\tlists_itself\tlists_start\tresult")
for lang, url in sorted(base.items()):
    if not url.startswith(("http://", "https://")):
        print(f"{lang}\t{url}\t\t\t\t\tNOT_ABSOLUTE")
        continue
    try:
        got, code, page = fetch(url)
    except Exception as e:
        print(f"{lang}\t{url}\tERROR {e}\t\t\t\tFETCH_ERROR")
        continue
    alt = alternates(page)
    self_ok = url in alt.values()
    back_ok = final in alt.values() or start in alt.values()
    result = "OK"
    if got != url:
        result = "REDIRECTED"
    elif not (self_ok and back_ok):
        result = "NOT_RECIPROCAL"
    print(f"{lang}\t{url}\t{code}\t{html_lang(page)}\t{self_ok}\t{back_ok}\t{result}")

公開前にはトップ・アクセス・料金・よくある質問など事実の多いページで、保守では毎月数ページを選んで動かします。NOT_RECIPROCAL や REDIRECTED が出たら、そのページの翻訳の紐づけ（プラグインの「翻訳」の設定）とURLを確かめます。Googleは lang 属性を言語の判定に使わないとしていますが、画面の読み上げや他のツールのために、言語ごとに正しい値にしておきます。

構造化データと llms.txt：言語ごとに何を変えるか

会社や店の構造化データ（LocalBusiness や Organization）は、どの言語のページでも同じ1つの会社・店を表します。言語ごとに別の会社のように見えないよう、次のようにするのがおすすめです（これはGoogleの決まりではなく、この記事のすすめ方です）。

  1. 会社・店のノードの @id は全言語で同じにする（例：https://example.jp/#business）。電話番号・住所・営業時間の値も同じにする。
  2. name はその言語のページで通じる表記にし、正式な日本語の表記を alternateName に入れる（逆でもよいが、全言語で同じ方針にする）。
  3. ページのノード（WebPage など）の inLanguage を、そのページの言語にする（ja・en・zh-Hant など）。
  4. FAQPage などの質問と答えは、そのページに見えている言語の文章で書く。見えていない言語の質問を構造化データだけに入れない。
  5. llms.txt はサイトの直下に1つ置くのが一般的です。主な言語で書き、他の言語のトップページへのリンクを載せておくと、どの言語の入口があるかが伝わります。

WordPressでの手順（Polylang・WPML と Nurevo AEO）

WordPressの多言語プラグインの代表は Polylang と WPML で、どちらも hreflang を自動で出します（Polylang の説明、WPML の説明）。違いと確かめる場所は次のとおりです。

  1. Polylang：WordPressの言語の設定（en_US など）を hreflang の形（en-US）に変えて出します。x-default は初期設定ではトップページだけで、他のページにも出したい場合はフィルター（pll_rel_hreflang_attributes）で足すと説明されています。
  2. WPML：言語の設定の画面で、言語ごとに hreflang のコードを変えられます（地域を付けるなど）。WPMLは誤った形式のコードを警告できないと説明しているので、入力したコードを上の表で確かめます。
  3. SEOプラグインやテーマが別に hreflang を出していないか、ページのソースで hreflang の行が1組だけかを確かめます。
  4. 言語ごとのページで、ブラウザの「ページのソースを表示」から html の lang 属性と hreflang を見て、上のスクリプトでも確かめます。
  5. 無料のプラグインNurevo AEOは、ページの構造化データの inLanguage に WordPress の言語の設定（get_bloginfo('language')）を入れます。Polylang・WPML 専用の処理はないので、言語ごとのページで inLanguage がその言語になっているかを確かめてください。会社・店の情報は1組の設定なので、全言語で同じ事実が出ます。llms.txt はサイトの言語で1つ作ります。
  6. 公開の前に、全言語の主要なページについて、営業時間・価格・電話番号を日本語のページと見比べます。

言語ごとの確かめ方

  1. 質問の一覧を言語ごとに作る（例：「◯◯駅 近く そば 英語メニュー」を英語・中国語・韓国語で）。直訳ではなく、その言語の人が実際に聞きそうな言い方にする。
  2. AIの設定の言語や、使うアカウントの言語を変えて聞き、回答の言語・出典のURLの言語・事実が正しいかを記録する。
  3. Search Console の検索パフォーマンスで、ページを /en/ などのディレクトリで絞り、国ごとの表示回数を見る。
  4. アクセス解析で、AIのサービスからの流入を言語のディレクトリごとに見る。
  5. 誤った事実が出たら、出典のページの言語と更新日を確かめ、その言語のページを直す。

AIの回答は聞くたびに変わるので、1回の結果で判断せず、月ごとの記録で比べます。測り方の全体はAIでの登場率の測り方にまとめています。

見積もりと保守契約に書くこと

項目書いておくこと
翻訳誰が訳すか（お客様・翻訳会社・機械翻訳＋確認）。機械翻訳だけで公開しないこと、確認する人
訳すページの範囲全ページか、トップ・アクセス・料金・FAQなど事実の多いページだけか。訳さないページの扱い
事実の更新営業時間や価格を変えたとき、全言語をいつまでに更新するか。更新を頼む窓口
技術の範囲URLの分け方、hreflang、言語の切り替えのリンク、構造化データ、llms.txt の設定
毎月の確認hreflang の相互の確認（数ページ）、言語ごとの事実の見比べ、言語ごとのAIの質問の記録

新しくサイトを作るときの工程全体は新規制作でAI検索に対応する手順、月額のサービスの組み立て方はAI検索対策を月額サービスにする方法にまとめています。

公開前と毎月のチェックリスト

  1. 言語ごとに別のURLがあり、1つのページには1つの言語だけが書かれている
  2. IPアドレスやブラウザの言語による自動の転送をしていない。各ページに他の言語へのリンクがある
  3. hreflang が全言語のページで相互に載っていて、完全なURL・正しいコードで書かれている
  4. 訳していないページや、転送・noindex のページを hreflang に載せていない
  5. x-default を決めている（言語を選ぶページか英語版）
  6. html の lang 属性と、構造化データの inLanguage がページの言語になっている
  7. 会社・店の構造化データが全言語で同じ @id・同じ電話番号・住所・営業時間
  8. 営業時間・価格・予約の方法が、全言語で日本語のページと同じ
  9. 機械翻訳した文章を、その言語が分かる人が確認している
  10. 言語ごとのAIへの質問と回答を、日付つきで記録している

制作会社がNurevoを使う場合

お客様のサイトごとに無料のプラグインを入れると、構造化データ・llms.txt・AIのクローラーの許可を整えたうえで、言語ごとの確認を保守の項目にできます。Standardは月3,000円です。パートナー制度はパートナーのページをご覧ください。

よくある質問

hreflang を入れれば、ChatGPTやPerplexityで各言語のページが出典になりますか？

分かりません。ChatGPT・Perplexity・Claude が hreflang を使うという公式の説明は見つかっていません。試した例では英語版を出典にすることも多かったので、どの言語のページが出典になっても事実が正しい状態にしておくことを優先してください。

機械翻訳で多言語のページを作ってもいいですか？

GoogleはAIで訳した内容をそれだけでスパムとはしていませんが、価値の少ないページを大量に作ることはスパムのポリシーの対象です。機械翻訳を使う場合も、その言語が分かる人が事実と表現を確かめてから公開してください。

全ページを翻訳しないといけませんか？

いいえ。トップ、アクセス、料金、予約、よくある質問など、その言語の利用者が必要とするページから始めて構いません。訳していないページは、その言語のページとして作らず、hreflang にも載せません。

ブラウザの言語で自動的に英語のページへ切り替えるのはだめですか？

Googleは自動の転送を避け、他の言語へのリンクを置くことをすすめています。クローラーは言語の指定なしで来ることが多く、自動の転送があると一部の言語のページが読まれないおそれがあります。

日本語の店名と英語の店名、どちらを構造化データに入れればいいですか？

そのページの言語で通じる表記を name に、もう一方を alternateName に入れる形がおすすめです。全言語で会社・店のノードの @id と、電話番号・住所・営業時間の値は同じにします。

中国語は簡体字と繁体字の両方が必要ですか？

お客様の利用者によります。台湾・香港からの利用者が多い場合は繁体字（zh-Hant や zh-TW）、中国本土からが多い場合は簡体字（zh-Hans や zh-CN）を用意し、両方作るならそれぞれ別のURLにして hreflang で結びます。

多言語にすれば、海外の人のAIの回答に出るようになりますか？

保証はできません。AIの回答は日や聞き方、使う人の言語で変わります。多言語のページを整えることは、出たときに正しい事実で紹介され、その言語のページへたどれるようにするための前提です。

お客様のサイトを、AIがどう読んでいるか確認

無料のチェックは登録不要です。URLを入れると、構造化データ・llms.txt・AIのクローラーの許可の状態が分かります。言語ごとのページのURLでも試せます。
