WordPress保守会社のAI検索対策：保守作業でAIに読めなくなる事故を防ぐチェックリスト

WordPress保守会社がAI検索対策でまずやるべきことは、新しい施策を足すことより、日々の保守作業（移転、セキュリティ・CDNの設定、プラグインやテーマの変更、robots.txtの編集）が、AIのクローラや構造化データを壊していないかを毎回確かめることです。確認は「作業のたび」「毎月」「移転のとき」の3つのタイミングに分けると、既存の保守の流れに無理なく入ります。

作成日：2026年11月10日（JST）。Cloudflare と WordPress の仕様は同日に各公式ドキュメントで確認したものです。仕様は変わることがあるため、作業の前に最新の情報をご確認ください。

この記事は、すでにWordPressの保守・運用を請けている会社やフリーランスの方向けです。AI検索対策を月額サービスとして設計する方法（作業範囲・価格）は制作会社がAI検索対策を月額サービスにする方法にまとめています。ここでは、保守の現場で起きやすい「気づかないうちにAIから見えなくなる」事故と、その見つけ方に絞ります。

なぜ保守会社がAI検索対策の要になるのか

ChatGPT・Perplexity・GoogleのAI機能が事業について答えるとき、使われるのはクローラが読めたページと、そこに書かれた事実です。Googleは、AI OverviewsやAI Modeに表示されるための追加の要件や特別な最適化はなく、通常のSEOのベストプラクティスが当てはまると説明しています（Google検索セントラル：AI機能とウェブサイト）。OpenAIは、OAI-SearchBotを拒否したサイトはChatGPTの検索回答に表示されないとしています（OpenAI：クローラの概要）。

つまり、AIに読まれるかどうかは「クローラが入れるか」「インデックスを拒否していないか」「構造化データと本文の事実が正しいか」で決まり、これらはどれも保守作業で変わるものです。サーバー移転のときに残った設定、セキュリティを強めたときのボット対策、SEOプラグインの乗り換えなど、善意の作業がAIからの見え方を止めてしまうことがあります。

しかも、この種の事故はサイトを人が見ても気づけません。表示は普段どおりで、問い合わせが少し減ったように見えるだけです。だからこそ、サイトの中を定期的に触っている保守会社が確認を持つのがいちばん確実です。なお、AIの回答は同じ質問でも日や回によって変わります。ここでの確認は「AIが読める状態を保つ」ためのもので、AIに必ず表示されることを約束するものではありません。

移転のあとに残りやすい「インデックスしない」設定

WordPressの「検索エンジンがサイトをインデックスしないようにする」は、WordPress 5.3 から robots.txt に Disallow を書く方法をやめ、ページに robots メタタグ（noindex, nofollow）を出す方法に変わりました（Make WordPress Core：検索エンジンにインデックスさせない仕組みの変更）。そのため、robots.txt だけを見て「問題なし」と判断すると見落とします。HTMLソースで meta name='robots' を確認しましょう。

同じ記事では、開発・ステージング環境には、画像やPDFも含めてサーバー側で X-Robots-Tag: noindex, nofollow のヘッダーを付ける方法を勧めています。これはWordPressの設定ではなくサーバーやホスティングの設定なので、本番に切り替えたあとにヘッダーが残っていないか、レスポンスヘッダーで確かめる必要があります。

セキュリティ・CDN・WAFでAIのクローラを止めていないか

保守会社がセキュリティを強めるときに、いちばん気づきにくいのがここです。ボット対策の多くは、AIのクローラを「よくわからない自動アクセス」としてまとめて止められます。

例えば Cloudflare には、AIのクローラとエージェントへの対応を、用途ごとに「Search（質問に答えるために収集・インデックスするもの）」「Agent（人の代わりにリアルタイムで動くもの）」「Training（モデルの学習に使うもの）」に分けて、ブロック・広告のあるページだけブロック・許可から選ぶ設定があります。公式ドキュメントでは、新しいドメインは3つとも「許可（ブロックしない）」が初期値とされています。一方で、Training には学習と検索の両方に使う「兼用のクローラ」も含まれると説明されています（Cloudflare：AI Crawler and Agent access policies、2026年11月2日更新）。学習を止めるつもりで設定を変えたとき、何が止まるのかを設定画面の説明で確認してから適用しましょう。

確認には、サーバーのアクセスログがいちばん確実です。OAI-SearchBot や PerplexityBot などのリクエストが来ているか、応答が 200 か 403 かを見ます。curl でユーザーエージェントだけを名乗って試す方法もありますが、Cloudflare は「検証済みボット」を署名・公開されたIPアドレスの一覧・逆引きDNSなどで見分けるとしているため（Cloudflare：Verified bots）、名乗っただけのリクエストは本物のクローラと同じ扱いにならないことがあります。テストの結果だけで判断しないようにしましょう。

クローラの名前と用途は、各社のページで確認できます（OpenAI、Perplexity）。学習用のクローラ（GPTBot など）を許可するかどうかはAI検索への表示とは別の判断なので、保守会社が決めず、お客様に選んでもらうのが安全です。

保守チェックリスト：作業のたび・毎月・移転のとき

次の3つに分けて、今の保守の手順書にそのまま足せる形にしています。

  1. 【作業のたび】プラグイン・テーマの更新や設定変更のあと、トップページと主要ページ（サービス・料金・アクセス・FAQ）のHTMLソースで、noindex がないこと、application/ld+json が1つの事業として出ていることを確認する。
  2. 【作業のたび】セキュリティ・CDN・WAFの設定を変えたら、変えた内容と日付を記録し、翌日以降のアクセスログでAI検索のクローラの応答コードを見る。
  3. 【毎月】/robots.txt と /llms.txt が 200 で返り、内容が意図どおりか確認する。llms.txtの書き方
  4. 【毎月】お客様の営業時間・料金・住所・サービスに変更がなかったか聞き、ページ・構造化データ・llms.txt・外部のプロフィールを突き合わせる。
  5. 【毎月】決めた質問をAIに聞き、事業が名前で出たか、サイトが引用されたかを記録する（任意。手順はAIでの登場率の測り方）。
  6. 【移転のとき】「検索エンジンがサイトをインデックスしないようにする」のチェック、X-Robots-Tag ヘッダー、Basic認証、IP制限が本番に残っていないかを確認する。
  7. 【移転のとき】サーバーに robots.txt ファイルを持ち込んでいないか、持ち込んだならその内容が意図どおりかを確認する。
  8. 【SEOプラグインを変えるとき】構造化データの出し方が変わるので、重複と抜けを確認する。SEOプラグインに店舗の構造化データを足す方法

多くの保守報告にはすでに「更新したプラグイン」「バックアップ」「稼働状況」の行があります。そこに上の数行を足すだけで、AI検索対策を保守の一部として説明できます。AIでの見え方は、すべての回答を観測したものではなくサンプルなので、1回の結果で判断しないことも報告に書き添えましょう。

お客様への説明と契約で気をつけること

  1. AIに表示されること・順位は約束しない。約束するのは、確認の頻度と項目、見つけたときの対応です。
  2. 学習用クローラの許可・拒否は、お客様の判断として記録する。AI検索のクローラとは分けて説明します。
  3. プラグインの導入や robots.txt の変更は、事前にお客様に知らせる。導入のお知らせ文の例はパートナープログラムのページにあります。
  4. CDN・WAFの契約がお客様名義のときは、誰が設定を変えてよいかを決めておく。

Nurevo AEOで確認を回す場合

Nurevo AEOのWordPressプラグイン（WordPress.org）は無料で、0〜100のAEOスコアと直すべき項目のチェックリスト、構造化データ・llms.txt・AIクローラの許可設定を管理画面から整えられます。robots.txt に追加する記述は、/wp-admin/ などサイトの既存のルールをAIのクローラにも繰り返して適用します。Yoast SEO・Rank Math・All in One SEO・Slim SEO の構造化データには不足分だけを足し、二重に出しません。0.9.1 からは SEO SIMPLE PACK・VK All in One Expansion Unit とも、構造化データが重ならないように併用できます。

多くのサイトを保守している場合は、WP-CLI の wp nurevo status で、そのサイトの出力が有効か、構造化データ・llms.txt・AIクローラの設定のどれを公開しているかを確かめられます。設定は wp nurevo export / import でほかのサイトへ写せます（キーや接続情報は含まれません）。管理者は REST の GET /wp-json/nurevo/v1/status でも状態を読めます。まとめて導入する手順はパートナープログラムのページにあります。

正直に書くと、Nurevoの診断は、Nurevoのサービスがサイトのトップページ・robots.txt・llms.txtを取得して行うもので、AIのクローラとして取得するわけではありません。CDNやWAFがAIのクローラだけを止めている場合は、診断では分からないことがあります。その確認は、上のとおりアクセスログで行ってください。

AIでの見え方は、接続したFree・Standardのサイトなら毎月の無料AIチェック（Perplexityに3問）、Pro（月14,800円〜、ベータ）ならPerplexityでのAI登場率を継続して計測できます。評価基準の自動更新はStandard（月3,000円）です。制作会社・保守会社向けには、自社ブランドの月次レポートや、紹介したお客様の有料プランの月額の40%（Stripe手数料控除後）をお支払いする紹介報酬があります（条件はパートナープログラムをご覧ください）。

よくある質問

保守契約にAI検索対策を入れるには、何から始めればよいですか？

まず今の保守の手順書に、作業のあとの確認（noindex がないか、構造化データが出ているか）と、毎月の robots.txt・llms.txt の確認を足すところからです。新しい施策より、今のサイトがAIに読める状態を保つことが先です。

セキュリティを強めると、AI検索に出にくくなりますか？

設定しだいです。ボット対策やWAFがAI検索のクローラまで止めると、そのAIはページを読めません。用途ごとに許可・拒否を選べる設定もあるので、何を止めるのかを確認してから適用し、アクセスログで応答コードを確かめましょう。

robots.txt に問題がなければ、インデックスの拒否はしていないと言えますか？

言えません。WordPress 5.3 以降、「検索エンジンがサイトをインデックスしないようにする」は robots.txt ではなく robots メタタグで伝えます。サーバーの X-Robots-Tag ヘッダーでも拒否できるので、HTMLソースとレスポンスヘッダーの両方を確認します。

学習用のAIクローラは止めてもよいですか？

お客様の方針しだいです。学習用クローラ（GPTBot など）の扱いは、AI検索のクローラ（OAI-SearchBot など）とは別の判断です。保守会社が決めず、お客様に選んでもらい、その内容を記録しておきましょう。

AIでの見え方まで毎月測る必要がありますか？

必須ではありません。保守として最低限やるべきなのは「AIが読める状態か」の確認です。見え方の計測は、お客様が希望する場合に、決めた質問を同じ条件で確かめる形で追加すると無理がありません。

保守しているサイトを、AIがどう読んでいるか確認

登録不要の無料チェックで、構造化データ・llms.txt・AIクローラ設定の現状がわかります。保守の月次確認の入口にお使いください。
