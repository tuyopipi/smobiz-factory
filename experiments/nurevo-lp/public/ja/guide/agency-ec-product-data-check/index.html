ECサイトの保守に「商品データの整合チェック」を足す方法：制作会社のための手順と報告の型

ネットショップの保守契約には、同じ商品について「ページに見えている価格と在庫」「ページの構造化データ（Product・Offer）」「Merchant Centerなどのフィード」「llms.txt とAIの回答」の4か所の値が一致しているかを、毎月、決まった商品で突き合わせる作業を足すのがおすすめです。Googleは、フィードの価格がページや構造化データと一致しないと商品が不承認になることがあり、アカウントの停止につながる場合もあると説明しています。AIの回答も、価格を古いまま答えることがあります。この記事では、ずれが起きる原因、点検の手順とスクリプト、報告の文例、契約への書き方をまとめます。

作成日：2026年11月23日（JST）。対象は、ネットショップを作る・保守する制作会社、WordPress（WooCommerce）の保守会社、ECの運用を預かっているフリーランスの方です。Merchant Centerの説明は、この記事の作成時点のGoogleのヘルプに合わせています。画面や条件は変わることがあるので、作業の前に各リンク先を確かめてください。

AIの回答は日や聞き方によって変わります。商品データをそろえることは、AIや検索に正しく読まれるための前提で、AIの回答に出ることや順位を保証するものではありません。

よく読まれている記事と、足りないこと

「ECサイト 保守 商品データ」「Merchant Center 価格の不一致」「product data consistency」などで上位に出る日本語8本・英語8本を、2026年11月23日に読みました。日本語では、Salesforceのチェックリスト（11月17日更新）、ShopifyのECの構造化データの解説（7月23日）、ネットショップ担当者フォーラム（2025年11月7日）、コマースピック（7月21日）、Business Insider Japan（9月28日）、Shopifyのヘルプなど。英語では、Search Engine Journal（6月10日）、BelVG（6月12日）、Yotpo（10月20日更新）、Sitebulb（3月31日）、TechWyse（9月7日）、DesignRush（10月5日）、Redefine Webの保守プランの記事（9月22日更新）、dev.toのMerchant Centerの記事です。

「ページ・構造化データ・フィードの値をそろえる」ことが大事だという点は、ほとんどの記事で一致していました。一方で、制作会社が保守の作業として毎月回すときに必要な次の点は、ほとんど書かれていませんでした。

なぜ保守の項目にするのか：Googleの扱いとAIの回答

商品データのずれは、一度直しても、セールや値上げ、在庫の変化のたびに起きます。月に一度、決まった手順で確かめる保守の項目にしておくと、お客様から言われる前に見つけられます。Googleのヘルプには、次のように書かれています。

Googleの説明出典
Googlebotは商品ページを定期的に読み、フィードの価格を、ページに表示された価格や構造化データ（ある場合）と比べる。一致しないと商品が不承認になることがあり、アカウントの停止につながる場合もあるMerchant Center ヘルプ：価格の不一致
ページのHTMLの価格は、Merchant Centerの価格と正確に一致している必要がある。読み込みのあとにJavaScriptで入れた価格はエラーになる。ページとフィードが一致していても、構造化データが違えば、構造化データを直すまで不承認が続くMerchant Center ヘルプ：価格の不一致
審査の担当者が価格や在庫のずれを見つけると、アカウントへの警告や、商品の事前の不承認になることがある。審査は7営業日かかり、審査に通らないと7営業日の待機期間があるMerchant Center ヘルプ：フィードとページの不一致
「自動での商品の更新」をオンにすると、Googleがページの値で価格を直すことがある。ただし、ずれは引き続き重大なエラーとして扱われ、アカウントの停止につながりうるMerchant Center ヘルプ：自動更新と価格の不一致
構造化データは、サーバーが返すHTMLに入っていて、利用者に見えている値と一致している必要がある。自動での商品の更新には price・priceCurrency・availability・condition が必要Merchant Center ヘルプ：構造化データの設定

AIの回答の側でも、価格の誤りは起きています。Business Insider Japan が紹介した Product.ai の調査（2026年9月）では、ChatGPT・Claude・Gemini・Perplexity に220の買い物の質問を5回ずつ聞き、価格を確かめられた913件の回答のうち、今の価格と一致したのは85%でした（Business Insider Japan。Googleは、調べたのは開発者向けのAPIで、一般向けのアプリではないと説明しています）。ショップ側でできるのは、AIが読む元のデータを、どこで読まれても同じ値にしておくことです。

また、GoogleのAIモードと通常の検索で、同じ商品の価格が一致しなかった例が38.1%あったという、Productriseのデータを紹介する記事もあります（TechWyse。8月の約3週間・200万件以上の掲載を追った集計で、原因は示されていないと記事に書かれています）。ChatGPTのショッピングでは、Profoundが追っている質問で、フィードとつながった情報源からの商品の推薦が7月に61.54%になったと報じられています（DesignRush。ChatGPT全体の数字ではありません）。フィードとページがずれていると、どちらの値がAIに使われるかを、ショップ側では選べません。

ずれが起きるよくある原因と直し方

Googleのヘルプに挙がっている原因のうち、制作会社が保守で見つけやすいものを、直し方と一緒に並べました。

原因起きること直し方
セールの開始・終了の時刻やタイムゾーンの設定違いフィードかページのどちらかが、セール前・セール後の価格のままフィードの sale_price_effective_date とショップのセールの設定を同じ日時・タイムゾーンにする
フィードの更新が1日1回などで、ページより遅い値上げ・値下げや在庫切れのあと、しばらくずれるページの更新のすぐあとにフィードを更新する設定にする。自動での商品の更新も検討する
ページのキャッシュ（プラグイン・サーバー・CDN）が古い管理画面では新しい価格なのに、公開されたHTMLは古い価格価格を変えたときに商品ページのキャッシュが消える設定か確かめる
価格をJavaScriptで後から表示しているGooglebotが読むHTMLに価格がない、または違うサーバーが返すHTMLに価格と構造化データを入れる
バリエーションの初期表示ページで最初に選ばれている色・サイズの価格と、フィードの商品の価格が違うフィードの各バリエーションのURLで、その色・サイズが選ばれた状態になるようにする
会員価格・まとめ買い・最小注文数誰でも払える価格とフィードの価格が違うフィードとページの目立つ価格を、誰でも払える価格にそろえる。最小注文数がある場合は、その数の合計価格を出す
構造化データが2つ出ている（テーマ・プラグインの重複）Product・Offer が2組あり、片方が古い価格どのプラグインが出しているかを確かめ、1つにする
税込・税抜の入力と表示の設定表示は税込なのに、構造化データやフィードが別の数字ショップの価格の入力と表示の設定を確かめ、4か所で同じ数字が出るようにする

原因の一覧は、価格の不一致とフィードとページの不一致のヘルプをもとに、制作会社の作業の言葉に直したものです。

毎月の点検の手順

  1. 点検する商品を決める（例：30件）。売れ筋の上位、いまセール中の商品、今月価格や在庫を変えた商品、バリエーションのある商品、新しく追加した商品を、少しずつ入れる。毎月すべてを見るより、ずれやすい商品を確実に見るほうが役立ちます。
  2. Merchant Centerの「診断」で、価格・在庫の不一致の警告や不承認がないかを先に見る。期限のある警告があれば、ほかの作業より先に対応する。
  3. フィードから、点検する商品の id・link・price・availability を書き出す。
  4. 下のスクリプトで、フィードの価格・在庫が、ページのJSON-LDに入っているかを比べる。
  5. スクリプトで OK になった商品も、5件ほどはブラウザで開き、カートに入れる前の価格・在庫・送料の表示が同じかを目で見る（スクリプトは見えている文字までは比べません）。
  6. llms.txt を出している場合は、点検した商品の価格・在庫が載っていれば一致を確かめる。
  7. AIに、点検した商品の価格・在庫・送料を数問聞き、日付と一緒に質問と回答を残す。
  8. ずれていた商品は、原因の表に当てはめて直し、翌月に同じ商品をもう一度見る。
# 使い方：python3 check_offers.py feed.csv > result.tsv
# feed.csv は id, link, price, availability の列を持つCSV
# （Merchant Center の商品一覧の書き出しや、フィードのファイルから列を選んだもの）
# 結果：OK＝フィードの価格・在庫がページのJSON-LDにある／MISMATCH＝ずれている
#       NO_JSONLD＝ページにProduct・Offerがない／FETCH_ERROR＝ページを取れない
import csv, json, re, sys, urllib.request

def offers(node):
    if isinstance(node, list):
        for n in node:
            yield from offers(n)
    elif isinstance(node, dict):
        if "@graph" in node:
            yield from offers(node["@graph"])
        types = node.get("@type", [])
        types = types if isinstance(types, list) else [types]
        if "Product" in types or "ProductGroup" in types:
            yield from offers(node.get("offers", []))
            yield from offers(node.get("hasVariant", []))
        if "Offer" in types or "AggregateOffer" in types:
            yield node

def num(text):
    m = re.search(r"\d[\d,]*(?:\.\d+)?", str(text or ""))
    return float(m.group(0).replace(",", "")) if m else None

def page_offers(url):
    req = urllib.request.Request(url, headers={"User-Agent": "Mozilla/5.0 (offer-check)"})
    html = urllib.request.urlopen(req, timeout=20).read().decode("utf-8", "replace")
    found = []
    for block in re.findall(r'<script[^>]+application/ld\+json[^>]*>(.*?)</script>', html, re.S | re.I):
        try:
            found += list(offers(json.loads(block)))
        except ValueError:
            pass
    return found

print("id\tfeed_price\tjsonld_price\tfeed_availability\tjsonld_availability\tresult")
for row in csv.DictReader(open(sys.argv[1], encoding="utf-8-sig")):
    try:
        found = page_offers(row["link"])
    except Exception as e:
        print(f"{row['id']}\t{row['price']}\t\t{row['availability']}\t\tFETCH_ERROR {e}")
        continue
    prices = sorted({num(o.get("price", o.get("lowPrice"))) for o in found} - {None})
    avail = sorted({str(o.get("availability", "")).rsplit("/", 1)[-1] for o in found})
    feed_avail = row["availability"].replace("_", "").lower()
    ok_price = num(row["price"]) in prices
    ok_avail = any(a.lower() == feed_avail for a in avail)
    result = "OK" if ok_price and ok_avail else ("NO_JSONLD" if not found else "MISMATCH")
    print(f"{row['id']}\t{row['price']}\t{','.join(f'{p:g}' for p in prices)}\t{row['availability']}\t{','.join(avail)}\t{result}")

フィードとページのJSON-LDを比べるスクリプトの例です（Python 3、標準ライブラリだけ）。お客様の承諾を得て、サーバーに負担をかけない数（数十件）で使ってください。

AIの回答の確かめ方

AIの回答は、ショップのデータを直してもすぐには変わりません。毎月同じ質問を聞き、変化を記録するのが現実的です。

  1. 質問は、お客様が実際に聞きそうな形にする。例：「◯◯ショップの△△（商品名）はいくら？」「△△は在庫がある？」「◯◯ショップの送料は？」「◯◯ショップで返品できる？」。
  2. ChatGPT・Perplexity・GoogleのAIモードなど、聞いたAI・日付・回答・出典のURLを表に残す。回答に出典があれば、どのページ（自社の商品ページ、モール、比較サイト）から答えているかも残す。
  3. 古い価格や在庫を答えていて、出典が自社のページなら、そのページのキャッシュと構造化データを確かめる。出典がモールや比較サイトなら、そちらの掲載をお客様に直してもらう。
  4. 同じ質問でも回答は変わるので、1回の誤りで判断せず、数か月の傾向で見る。

お客様への報告の文例

毎月の報告は、件数と、お客様に決めていただきたいことが分かる形にしておくと、作業の価値が伝わりやすくなります。

保守契約への書き方

商品データの整合チェックは、作業の範囲をはっきり書いておかないと、「商品の登録や価格の変更も保守に入っている」と受け取られることがあります。誰が何をするかを、次のように分けておくと安心です。

区分例
保守に含む（制作会社）毎月◯件の点検、Merchant Centerの警告の確認、スクリプトと目視での突き合わせ、AIへの質問◯問、報告書、原因が設定やキャッシュにある場合の修正
お客様の作業商品の登録、価格・セールの決定と入力、在庫の更新、モール・比較サイトの掲載の更新
別見積もりフィードの仕組みの作り直し、テーマ・プラグインの入れ替え、全商品の一括の修正、ChatGPTなど新しいフィードへの申し込み
決めておくこと点検する件数と選び方、警告が出たときの連絡の早さ、報告の日、AIに聞く質問の一覧

米国の制作会社の保守プランの例では、フィードの監視を上位のプランに含め、下のプランでは追加の作業にしているものもあります（Redefine Web）。日本の価格の相場は、確かめられる資料がなかったため書いていません。

Search Engine Journal の記事では、ある店の1つの商品が、サイト・フィード・Googleが選んだ価格・構造化データで4つの違う価格になっていた例を挙げ、SEOの担当とフィードの担当が一緒に毎月確かめることをすすめています（Search Engine Journal）。保守の報告に、フィードの担当者（広告代理店やお客様の社内の担当）も入れておくと、直す人がすぐ決まります。

月額の保守としてのAI検索対策全体の組み立て方は、AI検索対策を月額サービスにする方法にまとめています。

WordPress（WooCommerce）での手順（Nurevo AEOを使う場合）

無料のプラグインNurevo AEOを使うショップでは、点検する場所が次のようになります。Nurevo AEOはMerchant CenterやChatGPTのフィードは作らないので、フィードは今お使いの仕組みで確かめてください。

  1. サイトの種類で「ネットショップ」を選ぶと（WooCommerceが有効なら提案されます）、店の情報を OnlineStore として出します。商品ページの Product・Offer は、WooCommerceの出力をそのまま使い、重ねて出しません。商品ページのJSON-LDを見るときは、WooCommerce以外のテーマやプラグインが2つ目を出していないかを確かめます。
  2. トップページには、商品の一覧（新しい順に最大30件）を OfferCatalog として載せます。価格がある商品だけに Offer を付け、在庫が分かれば在庫あり・なしを入れます。トップページも点検の対象に入れてください。
  3. llms.txt には、公開中で表示されている商品のうち新しい50件を、WooCommerceにある今の価格（セール中はセール価格）・通貨・在庫と一緒に載せます。WooCommerceに入力した価格の数字をそのまま使うので、税抜で入力して表示のときに税を足す設定では、税抜の数字になります。
  4. llms.txt は、投稿や商品を保存したとき、設定を変えたときに作り直され、それ以外は最大1日、前の内容を使います。予約したセールが始まった・終わった直後は、llms.txt の価格も確かめてください。
  5. 返品のページを設定すると、そのURLを返品ポリシー（MerchantReturnPolicy）として載せます。返品の条件そのものは、ページの文章で書きます。
  6. AIでの登場の確認は、つないだ Free・Standard のサイトで月に1回、Perplexityに3つの質問をして結果を表示します。Pro（月14,800円〜）では、計測を Perplexity で行います（ChatGPTは設定され次第）。

制作会社がNurevoを使う場合

お客様のショップごとに無料のプラグインを入れ、構造化データ・llms.txt・AIのクローラーの許可を整えたうえで、この記事の点検を保守の項目にすると、「何を直したか」と「AIにどう読まれているか」を同じ報告にまとめられます。Standardは月3,000円です。パートナー制度はパートナーのページをご覧ください。

毎月の点検のチェックリスト

  1. Merchant Centerに、価格・在庫の不一致の警告や不承認がない（あれば期限を確かめた）
  2. 点検する商品に、売れ筋・セール中・今月変更・バリエーションのある商品が入っている
  3. フィードの価格・在庫が、ページのJSON-LDの Offer と一致している
  4. ブラウザで見える価格・在庫・送料が、JSON-LDと一致している（数件の目視）
  5. セールの開始・終了の日時が、ショップとフィードで同じ
  6. 価格や在庫を変えたあと、商品ページのキャッシュが消えている
  7. Product・Offer の構造化データが1ページに1組だけ出ている
  8. 価格がサーバーのHTMLに入っている（JavaScriptで後から入れていない）
  9. llms.txt の価格・在庫が、サイトと一致している
  10. AIへの質問と回答を日付つきで残し、前の月と比べた

よくある質問

Merchant Centerを使っていないショップにも、この点検は必要ですか？

フィードがなくても、ページの表示と構造化データ、llms.txt、AIの回答の突き合わせは役立ちます。AIや検索がページの構造化データを読むので、表示と構造化データのずれを毎月確かめる価値があります。

「自動での商品の更新」をオンにすれば、点検はいりませんか？

Googleのヘルプでは、自動での更新で価格が直された場合も、ずれは引き続き重大なエラーとして扱われ、アカウントの停止につながりうると説明されています。自動の更新は保険と考え、元のずれを直す点検は続けてください。

全商品を毎月見る必要がありますか？

多くのショップでは、売れ筋・セール中・今月変更した商品・バリエーションのある商品を中心に数十件を見れば、ずれの多くを見つけられます。ずれが続く原因が見つかったら、その原因に当てはまる商品をまとめて確かめます。

スクリプトでMISMATCHになりました。まず何を見ればいいですか？

ブラウザでその商品ページを開き、見えている価格がフィードとJSON-LDのどちらと同じかを確かめます。見えている価格とJSON-LDが違えば構造化データやキャッシュ、見えている価格とフィードが違えばフィードの更新やセールの設定を疑います。

AIが古い価格を答えています。どうすればいいですか？

回答の出典を確かめます。自社のページが出典なら、そのページの表示・構造化データ・キャッシュを直します。モールや比較サイトが出典なら、その掲載の更新が必要です。直してもすぐに回答が変わるとは限らないので、数か月の記録で見てください。

価格の入力やセールの設定もお客様から頼まれます。保守に含めるべきですか？

契約で分けておくのがおすすめです。点検と、設定やキャッシュが原因のずれの修正は保守に、商品の登録や価格の決定はお客様の作業、または別料金の運用代行にすると、作業量が読みやすくなります。

商品データをそろえれば、ChatGPTやGoogleのAIに商品が出ますか？

保証はできません。AIの回答は日や聞き方で変わり、ほかの店の商品や口コミも使われます。そろえておくことは、出たときに正しい価格や在庫で紹介されるための前提です。

お客様のショップを、AIがどう読んでいるか確認

無料のチェックは登録不要です。URLを入れると、構造化データ・llms.txt・AIのクローラーの許可の状態が分かります。毎月の点検の前に使ってください。
